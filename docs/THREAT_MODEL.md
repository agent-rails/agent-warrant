# Threat Model

## Pillar 1 — Cross-org authority verification (`Grant`/`verify`/`Verifier`)

**Prevent:**
- A stolen `encoded_grant` string alone is not usable — verification requires a fresh `PossessionProof` signed by the private key matching the grant's `subject`. A captured grant with no proof, or a proof forged by a different keypair, is rejected. Covered by `tests/test_integration.py::test_stolen_grant_without_possession_proof_is_rejected`.
- A grant issued by an unresolvable/unknown issuer is rejected (`UnresolvableIssuer`, caught inside `verify()`, never propagated).
- An unsupported grant `version` is rejected before any other field is TRUSTED (not before parsed -- `Grant.decode()` parses the full JSON body, size-bounded to `MAX_ENCODED_GRANT_BYTES`, before the version check runs; the size bound closes the resource-exhaustion / RecursionError gap an unbounded parse would present).
- Every fail-closed exit in `verify()` uses narrow, named exception catches (`binascii.Error`, `ValueError`, `TypeError`, `json.JSONDecodeError`, `InvalidSignature`) around each parse/verify block — never a bare `except`, which would swallow a genuine bug (a `NameError` from a typo, an `AttributeError` from a real logic error) and misreport it as "invalid grant."
- `grant.issuer` is type-checked (`isinstance(..., str)`) before being passed to `resolver.resolve()` — an unhashable JSON value (a list or dict) as `issuer` otherwise makes a dict-based resolver's `.get()` raise `TypeError`, reachable pre-authentication (before any signature check) with an unsigned, 185-byte payload. Same pattern as the timestamp guards: a value that reaches a resolver/comparison/arithmetic operation must be type-checked first, not assumed safe because it came from a JSON object.
- **Revoked grants are rejected when a caller opts in.** `verify()` accepts an optional `revocation_checker` (`RevocationChecker`), checked LAST -- only once a grant has already passed every other check. A revoked `grant_binding` is rejected (`"grant has been revoked"`); an unreachable/unverifiable revocation source is ALSO rejected (`"revocation status unavailable: ..."`), never silently treated as "not revoked." See the dedicated Revocation subsection below for what this does and doesn't cover.

**Contain:** all failures fail closed (`valid=False`); `verify()` never raises regardless of how malformed either `encoded_grant` or `possession_proof` are — every field in both is attacker-controlled.

**Detect:** `VerifyResult.reason` names why a check failed, distinct for each failure class (malformed encoding, unsupported version, unresolvable issuer, invalid issuer signature, expired, invalid possession-proof signature, possession proof bound to a different grant, stale, non-numeric `iat`, revoked, revocation status unavailable).

## Revocation: what opting in actually buys you, and what it doesn't

Real, opt-in revocation checking is built (`RevocationChecker`, `StaticRevocationChecker`, `HttpRevocationChecker` -- see docs/DESIGN.md for why this is a small signed set, not StatusList2021). What it changes, precisely:

- **Freshness and rollback protection, part of the signed body.** The `RevocationList` format carries a signed `issued_at`, `expires_at`, monotonic `sequence`, and format `version`. A verifier rejects a list whose `expires_at` has passed, whose `issued_at` is in the future beyond a small skew, or whose `sequence` is lower than one it has already accepted for that issuer — treating any of these as `RevocationSourceUnreachable` (fail-closed), never a silent "not revoked." This closes a gap: an old signed list (e.g. an empty one from before a binding was revoked) replayed from a compromised CDN/cache/backup could otherwise verify OK and silently suppress every later revocation forever. **Precise residual, disclosed:** `expires_at` is the durable defense (survives a process restart); the `sequence` monotonic check is per-`HttpRevocationChecker`-instance in-memory state, so after a process restart a replayed older-but-still-unexpired list within its own validity window would be accepted again until it expires — keep `ttl_seconds` short if this matters. This is not thread-safe: concurrent `is_revoked()` calls on one checker instance race on the stored highest sequence.
- **Revocation status is bound to the grant's authenticated issuer.** `is_revoked(issuer, grant_binding)` takes the grant's own already-authenticated issuer; each checker is bound to one expected issuer and rejects unless `list.issuer == expected_issuer == grant.issuer`. This closes a gap where, in a multi-issuer or shared-checker deployment, issuer B's authentic (and empty) revocation list could vouch "not revoked" for issuer A's grant.
- **Revocation-list parsing is strict.** `from_json_bytes` whitelists the exact expected keys (rejecting unknown/unsigned extension fields), rejects duplicate JSON object keys, and rejects duplicate bindings — narrowing the surface between what is transmitted and what is signed.
- **Default behavior is UNCHANGED.** A `Verifier`/`verify()` call with no `revocation_checker` (the default, `None`) behaves exactly as before this feature existed. If an issuer's private key is compromised, every outstanding `Grant` it signed remains forgeable and unrevocable until its own `expires_at` UNLESS the verifier has opted in. `ttl_seconds` remains load-bearing, not a convenience default -- opting into revocation is a verifier-side decision an issuer cannot force or assume. This is not a hypothetical residual risk: [Hugging Face's July 2026 incident post-mortem](https://huggingface.co/blog/agent-intrusion-technical-timeline) names over-broad, long-lived access as one of the two root-cause categories that let a real intrusion escalate across multiple production clusters -- the exact shape a short TTL alone (still the only default) only partially contains.
- **`HttpRevocationChecker` makes revocation availability a single point of failure for callers who opt in.** No caching means every `verify()` call using it is a network round trip; if the revocation endpoint is unreachable, EVERY verification fails (fail-closed, by design) for that caller -- an outage or an attacker taking down the revocation endpoint effectively takes down all verification for anyone who opted in. A caller choosing `HttpRevocationChecker` is trading availability for revocability; `StaticRevocationChecker` (caller-managed fetch/cache) avoids this at the cost of the caller owning freshness themselves.
- **No anonymity-set privacy property.** Unlike StatusList2021's whole-bitstring-fetch design, `HttpRevocationChecker` asks about one specific `grant_binding` per call -- a revocation source can observe which grant is being checked, when. Accepted for this project's actual shape (small, known verifier population per issuer, not an anonymous public one); see docs/DESIGN.md.
- **No multi-issuer aggregation.** Each `RevocationList` is single-issuer; a verifier trusting multiple issuers needs one checker (or one fetch) per issuer. Not built: a merged, multi-issuer revocation view.

## Explicit non-goals

- **VC-spec conformance.** `Grant` is VC-data-model-*shaped* (issuer, subject, claim, expiry, proof), not VC-spec-conformant. It carries no `@context` and no `credentialStatus` field, and must never emit a literal `type: VerifiableCredential`. A real foreign VC verifier ingesting this and reading the absence of `credentialStatus` as "permanently valid, not revocable" would be wrong in a subtler way now than before: this project's own revocation checking is real, but lives entirely outside the `Grant`'s own fields (see the Revocation section above) -- a foreign verifier has no way to discover or invoke it, and has no reason to know this project's convention either way.
- **Cross-verifier replay within the freshness window.** `PossessionProof` binds to a specific `Grant` (via `grant_binding`) and has a freshness window (`max_age_seconds`, default 60s) — but no audience/verifier binding. A passive observer who captures a valid `(grant, proof)` pair can replay it at *any* verifier within that window. This is the same residual `agent-guard`'s own `verify_pop` has (a generous, non-single-use freshness window, not a nonce-tracked one), disclosed there for the same reason. Not closed — would need an `aud` field and a real reason (multi-verifier deployments) before adding that complexity.
- **Encoded-grant malleability.** `verify()` re-canonicalizes the decoded body rather than trusting the transmitted bytes — deliberate, and confirmed robust: a re-ordered/re-whitespaced JSON body still verifies to the same `Grant` and the same `grant_binding`. A consequence, not a bug: many distinct encoded strings verify identically, so the encoded string itself is not a stable identity for replay-detection or dedup purposes. Callers needing a replay/dedup key MUST use `grant_binding` (or a hash of it), never the raw encoded string. This is also why revocation is keyed by `grant_binding`, not by a hash of the encoded string.
- **Multi-hop delegation chains.** A `Grant` is single-hop: one issuer, one subject, no representation of "A delegated to B, who sub-delegated a narrower scope to C." Microsoft's Agent Governance Toolkit's `AgentMesh Identity and Trust` spec (`docs/specs/AGENTMESH-IDENTITY-TRUST-1.0.md` — see `agent-guard/docs/DESIGN.md`'s citation for the caveat that this is one individual's project hosted under the `microsoft` org, not a centrally-built Microsoft product) states the property a chained version would need to hold: "Scope chains only narrow. Delegation can never grant more capabilities than the parent holds," enforced via hash-chained delegation records. Worth citing as the shape of the problem if multi-hop delegation becomes a real need — not built here, and not a small increment on `Grant`/`verify()`; monotonic-narrowing enforcement across a chain is a genuinely different verification problem than this project's single issuer-to-subject check.

## `DidWebResolver`: a new pre-authentication network surface

`PinnedResolver` performs zero trust verification — it's out-of-band key pinning (TOFU); the caller is responsible for how the pinned key mapping was obtained and trusted. `DidWebResolver` is real trust bootstrap (HTTPS + domain ownership, the same trust model as TLS today) — but it is a real HTTPS client embedded in the verification path, which `PinnedResolver` never was, and that has consequences worth naming explicitly:

- **Pre-authentication SSRF-shaped risk.** `verify()` calls `resolver.resolve(grant.issuer)` *before* the issuer signature is checked. With `PinnedResolver` this is a harmless local dict lookup regardless of what `grant.issuer` contains. With `DidWebResolver`, an attacker submitting a garbage, entirely unsigned grant can make the *verifying process itself* issue an outbound HTTPS request to a domain of the attacker's choosing — inherent to did:web's whole model, not a bug specific to this implementation (you cannot authenticate an identifier without first fetching what it points to). **Defended:** `https_fetch.py` resolves the target *once*, rejects the fetch if ANY resolved address is private/loopback/link-local/reserved/multicast/unspecified, pins the screened IP, and connects to that pinned IP directly — the hostname is used only for TLS SNI/certificate verification and the `Host` header, never re-resolved at connect time. Shared by `DidWebResolver` and `HttpRevocationListFetcher`, so a crafted `issuer` (or a malicious revocation-list URL) can't be used to probe internal infrastructure (e.g. cloud metadata endpoints) through this library. **The DNS-rebinding TOCTOU that a check-then-connect pattern has is CLOSED** by this resolve-once-then-connect-to-the-pinned-IP design — a name resolving to a public address at check time can no longer resolve to a private one at connect time, because there is no second resolution. **Residual, disclosed:** the initial `getaddrinfo` call itself uses the OS resolver's own timeout, not the per-fetch wall-clock budget below; a pathologically slow resolver can still delay a single fetch at the DNS step.
- **Total-time bound against slow-drip hosts.** The per-socket timeout is per-operation, not a total request deadline: a host dripping one byte just under the per-op timeout could otherwise hold a read open for a very long time (pre-auth, and concurrent garbage grants could tie up verifier workers). `https_fetch.py` installs a wall-clock watchdog that closes the connection once `timeout_seconds` elapses, bounding the total time a single fetch (connect + TLS + headers + body) can consume regardless of drip rate. Not built (judged out of scope for this version): per-host concurrency limiting — a caller expecting adversarial load should bound verifier concurrency itself.
- **No redirect following.** `https_fetch.py` uses `http.client`, which never follows redirects — only an exact `200` is accepted; every other status (3xx included) is surfaced as a fetch failure, not silently followed. Chosen specifically so a compromised or misconfigured did:web host (or revocation-list host) can't downgrade a resolution to plaintext HTTP via a `Location` header.
- **Key-selection is purpose-bound, not array-order-bound.** `DidWebResolver` requires the DID document's own `id` to equal the requested DID, requires a candidate `verificationMethod`'s `controller` to equal that DID, and — when the document declares `assertionMethod` — selects only the referenced method(s). A document with more than one eligible Ed25519 key and no single assertionMethod reference is rejected as ambiguous rather than resolved by array position. This closes a key-confusion path where a crafted document (mismatched `id`, attacker-controlled `controller`, a first wrong-purpose key, a different assertionMethod-referenced key) could otherwise elevate a non-assertion key into a grant-signing key.
- **Algorithmic-complexity DoS on key fields is bounded.** `publicKeyMultibase`/`publicKeyBase58`/JWK `x` values are length-capped *before* decoding (the base58 decoder is O(n²) big-int accumulation; a 65KB field took ~1 CPU-second, multiplied per `verificationMethod`), and the number of `verificationMethod` entries processed is capped.
- **Failure messages are generic.** Exception reasons that can reach a caller-visible `VerifyResult.reason` do not embed attacker-controlled host/port/path or raw remote response text — an internal-hostname/DNS-leak and log-injection risk. Network-layer failures surface a generic reason; detailed diagnostics stay in the chained exception traceback, not the public string.
- **Availability coupling.** Same shape as `HttpRevocationChecker` above: `DidWebResolver` does no caching, so an unreachable or slow did:web host makes every `verify()` call against that issuer fail, for every caller using this resolver. A caching wrapper is a natural follow-up, deliberately not built here (see docs/DESIGN.md).

## Note on `MAX_ENCODED_GRANT_BYTES`'s two independent defenses

The 16KB size cap and `decode()`'s `except RecursionError` both close the same
resource-exhaustion / never-raises gap, but on different interpreters. The cap was
measured against Python 3.14's own recursion threshold (~150,000 nesting levels);
CPython's actual recursion limits are much lower on other supported versions
(`requires-python = ">=3.10"` covers interpreters with recursion ceilings around
1000-3000). On those, the `except RecursionError` catch is the defense that actually
fires — the size cap alone does not make it unreachable. Both must be kept; neither
is redundant given the full supported-version range.

## Pillar 2 — Canonicalization (`canonical.py`)

**Prevent:** every signature (issuer signature over a `Grant`, holder signature over a `PossessionProof`) is computed over the same single canonicalization implementation — no inline `json.dumps` anywhere in `grant.py`, `issuer.py`, or `identity.py`. `agent-guard`'s own `pop.py` uses inline `json.dumps` (which predates this project's canonicalization discipline); mirroring it literally in `PossessionProof.prove()` would reintroduce the exact "two drifting implementations" risk this module exists to prevent, so `PossessionProof` routes through `canonical.py` instead.

**Explicit non-goal:** this is a deterministic JSON serialization (sorted keys, compact separators, UTF-8), not full RFC 8785 JCS conformance — no float-exponent-normalization edge cases are handled, because this project's own data model never signs a float that isn't a Unix timestamp, and non-finite floats (NaN/Infinity) are rejected outright rather than needing JCS's normalization rules.
