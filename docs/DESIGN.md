# Design

The "why" document. This project's design went through two full pre-code review cycles (Step 0 first-principles check, then two rounds of adversarial plan_validation) before any code was written — the full history lives at `~/identity-unification-plan.md` in the session that produced this package. This document is the durable summary of that history, not a replacement for it.

## The thesis

An agent from Team A needs to prove its delegated authority to a system run by Team B, with no shared infrastructure and no pre-established trust relationship beyond agreeing on a credential format. `agent-guard`'s own `Broker`/`Token` already solves a version of this problem — but with HMAC and a shared secret, which only works within one org. Whoever holds the secret can forge tokens; sharing it across an org boundary defeats the point. Cross-org verification structurally needs asymmetric signing instead. That's not a small increment on `Token` — it's a different trust architecture, which is why this is a separate package, not a feature bolted onto `agent-guard`.

## Why the Verifiable Credentials data model, not A2A's Agent Card

The obvious move was "adopt A2A's signed Agent Cards" (a real, standardized mechanism — JWS over JCS-canonicalized JSON, verified against an issuer's public key). Checked directly against the A2A spec: Agent Cards describe *what kind of agent this is and what it can technically do* — a capability manifest, like a business card. They do not describe *what this specific agent instance is authorized to do right now, on whose behalf, until when*. That's a claim, not a manifest — the W3C Verifiable Credentials data model (issuer, subject, claim, expiry, proof) is the correct shape for it. A2A's signing mechanism (JWS/JCS) is reusable in spirit; its data model is the wrong artifact for this problem.

**Important disclaimer, not a technicality:** `Grant` is VC-data-model-*shaped*, not VC-spec-conformant. It carries no `credentialStatus`/StatusList2021 revocation mechanism. It must never emit a literal `type: VerifiableCredential` — a real foreign VC verifier encountering that type with no `credentialStatus` would read "no revocation status" as "permanently valid," which is false. See `docs/THREAT_MODEL.md`.

## Why a raw public key, not `did:key`, for V1's issuer identifier

`did:key` is a public key wearing DID string-format syntax — it does not solve "how does the verifier get the issuer's key," it just formats a key that must still be obtained out-of-band. It was cut as ceremony without function. `did:web` (resolves via HTTPS + domain ownership, the same trust model as TLS certificates today) is the mechanism that actually delivers "verify without pre-established trust" — but it needs real resolution infrastructure (an HTTPS fetch), so it's a planned V2, not built here. V1 ships `PinnedResolver`: a raw, out-of-band-pinned public key, honestly named so nobody mistakes it for real trust verification. The `IssuerResolver` Protocol is kept in V1 specifically so adding `did:web` later is not a breaking change to the wire format or the calling convention — only a new resolver implementation.

## Why holder-binding, not a bearer credential

The single most important correction in this project's design history: an earlier draft set `subject = holder's public key` and called that "holder-binding," citing `agent-guard`'s own `PoPProof` as precedent. It wasn't actually holder-bound — `verify()`'s signature had no slot for a possession proof at all, so a public key sitting inertly in an issuer-signed grant is still a bearer credential; anyone who intercepts the encoded grant can replay it. This was caught by an adversarial pre-code review, not found in code — exactly the value of reviewing a design before writing it. `PossessionProof` (a separate, freshly-signed, grant-bound, freshness-windowed proof) is what actually closes the gap, and it genuinely mirrors `PoPProof`/`verify_pop`'s structure: a fresh proof, bound to a specific credential (`grant_binding`, analogous to PoP's `token_binding`), checked for freshness (`iat` + `max_age_seconds`).

**A residual, disclosed, not silently assumed away:** the freshness window alone doesn't bind a proof to a specific verifier. A captured `(grant, proof)` pair is replayable at any verifier within `max_age_seconds` (default 60s) — the same residual `agent-guard`'s own `verify_pop` has, disclosed there too. See `docs/THREAT_MODEL.md`.

## Two near-misses in `verify()`'s own review, worth naming so they don't recur

1. **Canonicalization drift, reintroduced inside the fix for a different bug.** `PossessionProof.prove()` was first described as mirroring `PoPKeypair.prove()` "exactly" — but `pop.py`'s own `prove()` signs its body with inline `json.dumps(...)`, not JCS. Adopting that literally would have reintroduced the exact "two drifting canonicalizers" anti-pattern this project's `canonical.py` module exists to prevent — inside the very commit meant to fix the holder-binding gap. Caught in a second review pass, not the first. `PossessionProof`'s signable body routes through `canonical.py` like everything else; the PoP precedent is structural (fresh proof, freshness window, credential binding), not literal (its serialization choice is not copied).
2. **An iat-type guard omitted, then a test that didn't actually prove it mattered.** `verify()`'s freshness check does arithmetic on an attacker-controlled `possession_proof.iat`; without an `isinstance`/`math.isfinite` guard (matching `agent-guard`'s own `pop.py` precedent exactly), a non-numeric `iat` raises instead of failing closed — the identical failure class `agent-guard`'s own PR #35 found and fixed in `verify_pop` itself. The first regression test for this used `replace(proof, iat=bad_iat)` *after* signing, which meant the possession-proof signature check caught the tampering first and the guard was never actually exercised — confirmed by mutation-testing the test itself (removing the guard didn't turn it red). Fixed by constructing a genuinely, validly-signed proof containing the bad `iat` from the start.

## Genericity vs. narrow primitives — a named tension, not resolved by fiat

There's a real pull toward designing this to also serve payment-authorization-style use cases (Cloudflare Wallets is a real, shipped comparable) or agent-workspace-style use cases, as a genuinely portable Layer-0 primitive. That's in tension with this project's own stated preference for narrow, deeply-verified primitives over speculative generality (the same principle `agent-guard`'s `DESIGN.md` states explicitly, and the same principle a review flagged on this exact plan). Resolution: build the narrow agent-authority claim, verified deeply. Let portability be an emergent property (would an unrelated team take it as-is) rather than a design-time goal that adds wallet/workspace-shaped fields before a second real consumer exists.

## External validation, checked live not assumed

Two independent vendors have shipped real, per-agent asymmetric-cryptography identity in 2026: [Cloudflare Wallets](https://blog.cloudflare.com/wallets/) (agent identity + payment authorization, spending caps) and [Block's Buzz](https://github.com/block/buzz) (per-agent Nostr keypairs, Schnorr/secp256k1-signed events, for chat/Git-forge audit-log integrity). Different curves, different data models, different problems -- but the same underlying instinct: agents need first-class cryptographic identity, not a shared secret or an inherited human credential. Worth citing as market validation for this project's general direction. Neither is an interop target: Buzz's signing scheme has no delegation/scoped-grant concept comparable to a `Grant`, and Cloudflare Wallets is a closed platform service, not a portable format.

A third data point, [Microsoft's Agent Governance Toolkit](https://github.com/microsoft/agent-governance-toolkit) (hosted under the verified `microsoft` GitHub org, but primarily one individual's project -- checked live: 857 of ~2000 commits from a single non-Microsoft-employee author; its "AARM"/"ATF" compliance badges are self- or single-person-verified, not independent standards bodies), arrives at a genuinely bigger version of this problem: its identity spec (`AGENTMESH-IDENTITY-TRUST-1.0.md`) states "Every agent has a human sponsor. No orphan agents" as an explicit design principle -- this project assumes that structurally (an `Issuer` is presumably run by an accountable org) but has never stated it outright. Worth stating explicitly rather than leaving implicit. Their `did:mesh:<hex>` identifier scheme is a custom, non-W3C-registered DID method -- the same "ceremony without function" critique this document already applies to `did:key` above would apply here too; not a reason to adopt it, a reason to feel good about the `did:web`-deferred-to-V2 call already made.

## Reuse, not reimplementation

- The crypto primitive (Ed25519) is the same one `agent-guard`'s own PoP already uses — not a new choice.
- The wire-format shape (`body_b64.signature`) echoes `agent-guard`'s own `Token` encoding (`agentguard_identity/token.py`) — a proven convention, not a new one, even though the underlying trust model (asymmetric vs. symmetric) is genuinely different.
- `Issuer`/`Verifier` holding their respective key/resolver as instance state, rather than threading them through every call site, mirrors `agent-guard`'s own `Broker` — a private key threaded through every call site is worse security hygiene than one held once, by the object that owns it. Named tradeoff: a long-lived `Issuer` keeps the private key resident in the heap longer than a bare `sign()` call would. The bare function remains available directly for callers wanting minimal key residency.
